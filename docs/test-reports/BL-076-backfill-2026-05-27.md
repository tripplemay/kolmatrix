## §3 SQL 直证（superuser 视角，绕过 RLS）

### 3.1 import phase 主指标（核心 acceptance）

```sql
SELECT
  (SELECT count(*) FROM kol WHERE last_synced_at > '2026-05-26T16:37:00Z'::timestamptz)   AS synced,
  (SELECT count(*) FROM kol WHERE created_at    > '2026-05-26T16:37:00Z'::timestamptz)    AS inserted,
  (SELECT count(*) FROM kol WHERE engagement_rate > 999.99)                                AS above_old_max,
  (SELECT count(*) FROM kol WHERE engagement_rate > 100)                                   AS above_outlier_thresh,
  (SELECT count(*) FROM kol WHERE (metadata->'flags'->>'engagement_outlier')::boolean)     AS outlier_flagged,
  (SELECT count(*) FROM kol)                                                               AS total_rows,
  (SELECT count(*) FROM audit_log WHERE action = 'kol.import_failed'
     AND created_at > '2026-05-26T16:37:00Z'::timestamptz)                                 AS import_failed;
-- → synced=1859 | inserted=474 | above_old_max=15 | above_outlier_thresh=157
--   outlier_flagged=157 | total_rows=4455 | import_failed=0
```

### 3.2 解读

- **`synced=1859`** — 1859 个 KOL 在本次运行中通过 upsert，证明 import.ts upsert path 全部走通
- **`inserted=474`** — 474 个 KOL 是新插入（`created_at > 16:37`），证明 14 天遗漏 KOL backfill 起效。**Apify-kol shift window 担忧不成立**（spec §1.4 中所担心的"遗漏 KOL 永久丢失"现象并未发生 — 474 ≥ 200 阈值）
- **`above_old_max=15`** — 15 行 engagement_rate ∈ (999.99, 99999.99]，这些行**100% 会在旧 Decimal(5,2) 下抛 numeric overflow**。F001 schema 扩容生效证据
- **`above_outlier_thresh=157` = `outlier_flagged=157`** — outlier 阈值（>100%）和 metadata.flags.engagement_outlier 写入完全一致，F002 adapter clamp + flag 写入闭环
- **`import_failed=0`** — F003 per-KOL try/catch 路径**未被触发**（因为 F001+F002 已经在 schema + adapter 层先拦截了所有可能的 overflow），但 catch 路径仍作为兜底防御保留。这表明三层防御中两层就已经达成核心目标
- **`total_rows=4455`** — 总 KOL 数（不含 active filter），比运行前 health 的 1397 active KOL 高，差额来自 `is_active=false` 或软删除的历史 KOL

### 3.3 全局 audit_log 状态

```sql
SELECT count(*) FROM audit_log WHERE action = 'kol.import_failed';
-- → 0
SELECT max(engagement_rate), min(engagement_rate) FROM kol WHERE engagement_rate IS NOT NULL;
-- → max=9137.06, min=0.00
```

DB 历史**没有**任何 `kol.import_failed` 记录（既不是本次运行没有，是 audit_log 表内零相关记录）— 这是 F003 catch 起效后预期状态（catch 没触发 = 没有写入）。

Max engagement_rate `9137.06` 被成功 store — 这一行单独就足以在旧 Decimal(5,2) 下让整 batch fail。

## §6 14 天遗漏 KOL 估算

| 项 | 数值 | 备注 |
|---|--:|---|
| 14 天每日 apify-kol 报告的 `discoverCount` | 2107-2567 / 日 | 取自 `/var/log/kolmatrix-kol-sync.log` 5/12-5/26 entries |
| 14 天累计 unique discover（去 daily 重复） | 不可精确测算 | apify-kol service 不返回 unique-since 计数 |
| 本次 backfill `inserted` | **474** | tenant_platform_externalId unique key 自动 dedupe，已存在 KOL 不重复 |
| 本次 backfill `updated` | 1859 - 474 = **1385** | 已存在 KOL last_synced_at 刷新 |
| 估算 14 天累计遗漏 KOL（与本次结果对比） | ≥ 474 | 474 是 backfill 当日 apify-kol /kol 池中的"自上次成功 sync (5/12) 以来新增"约数 |

**评估：**

- spec §1.4 担心 `apify-kol 已 shift window` 导致部分 14 天遗漏 KOL 永久丢失
- 实测 474 inserted **远大于 spec §F004 acceptance 设定的 200 阈值**（"如 stats.inserted 数远小于 14 天预期遗漏 (如 < 200): 说明 apify-kol 已 shift window"）
- 结论：apify-kol 服务端窗口足够长，14 天遗漏 KOL **大部分已追回**
- 若仍有少量 KOL 永久遗漏，影响极小（业务层无 SLA 承诺 100% 覆盖），不再追加补救

## §7 三层防御协同效果

| 防御层 | 来源 | 实测拦截行 | 效果 |
|---|---|--:|---|
| L1: Schema Decimal(7,2) | F001 migration | 15 行 ∈ (999.99, 99999.99] | 所有这 15 行在旧 schema 下都会 throw |
| L2: Adapter Math.min clamp 99999.99 | F002 apify-kol.ts | 0 行（所有 raw 值都 ≤ 9137.06） | 当前 apify-kol 数据未触达 99999.99 上限；防御兜底未触发但保留 |
| L3: import.ts upsert try/catch + audit_log | F003 import.ts | 0 行（audit_log.kol.import_failed = 0） | L1+L2 已拦截，L3 兜底未触发但保留 |

**结论：** L1 (schema) 单层就足够拦截当前 prod apify-kol 数据流的所有 overflow case；L2 + L3 是 future-proof 防御（apify-kol upstream 数据分布漂移时仍能护住）。三层都有保留价值，未来若 apify-kol 输出超过 99999.99（极小概率），L2 clamp + L3 catch 共同形成"数据不丢 + 不让整 batch 死"的兜底。
