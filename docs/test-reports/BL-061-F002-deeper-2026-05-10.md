## §6 F003 全量 ≥80% 不达标 — 已上报 Planner（本报告记录证据，stop-on-systemic-issue）

跑同 spec §4.F003 SQL（superuser bypass RLS）：

```sql

       ROUND(COUNT(engagement_rate)::decimal/COUNT(*)*100, 1) pct

```

| tiktok    |   818 |          11 |  1.3 % |

| **合计**  | **1231** |     **83** | **6.7 %** |

**Acceptance 不达标：6.7 % < 80 %**（spec §4.F003 阈值）。

**根因排查（已完成）：**
1. KOLMatrix mapper 公式 `(totalLikes / postsCount) / followers * 100` 实现正确（`src/lib/kol-sync/adapters/apify-kol.ts:401-414`）—— 当 followers/postsCount/totalLikes 任一缺失或 0 即返回 NULL，符合 BL-059-F001 spec
2. 抽样 apify-kol service `GET /kol?platform=X&limit=20`（per-platform 各 20 行）：
   - tiktok: 20 行中 0 行 `postsCount>0 && totalLikes>0`（0 %）
   - youtube: 20 行中 5 行（25 %）
   - instagram: 20 行中 0 行（0 %）
3. 抽样 3 行 TT 原始 response：`{platform: "tiktok", followers: 778, postsCount: 0, totalLikes: 0}` — service 端字段就是 0
4. 结论：**apify-kol service 端 1228 个 hashtag-discovery KOL 未触发 profile 调用，profile-stats 为空**（仅 3 个 POST /admin/seeds 注入的 handle + ~80 个其他 KOL 有完整 profile）

**这是 fork 端数据 coverage 问题，不是 KOLMatrix mapper bug。** Per spec §5 Risk："F003 non_null_pct < 80% → Generator 上报 Planner，可能扩范围或起 hotfix" + role-context generator §"扩范围 vs 单点修的判断" → Generator 已 stop F003 implementation，等 Planner 裁决。
