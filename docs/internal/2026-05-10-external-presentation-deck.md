### Section 3 — 方案：Triad Workflow（5 min / 4 slides）

#### Slide 6 — 核心思想四要素（总览）

**布局：** 中央 KOLMatrix 项目盒子，外圈四个箭头指入

```
                ┌──── 三角色不重叠 ────┐
                │ Planner / Generator  │
                │ / Evaluator          │
                │ 无人评估自己工作      │
                └──────────────────────┘
                        ↓
       ┌────────────────────────────────────┐
       │  Git 作为                          │
       │  协作总线                          │
       │  (progress.json + .auto-memory/)  │
       └────────────────────────────────────┘
       ↑                                ↑
┌─ 状态机驱动 ─┐               ┌─ 记忆分层 ─────┐
│ 7 状态硬约束 │               │ T0/T1/T2       │
│ 越界即拦截   │               │ 跨会话/设备共享│
└──────────────┘               └────────────────┘
```

> **讲稿（70 秒）：**
> "Triad Workflow 解决三个难题靠四个核心机制。**第一：三角色不重叠**——Planner 做规划、Generator 写代码、Evaluator 验收，没有任何 agent 评估自己的工作，这条规则解决了"AI 自评失控"的难题。**第二：状态机驱动**——整个项目永远处于 7 个状态之一，每个状态只允许特定角色操作，AI 想越界做不到。**第三：Git 作为协作总线**——agent 之间不直接通信，全部通过 progress.json + .auto-memory/ 异步交接，可以跨会话、跨设备、甚至跨 AI 工具。**第四：记忆分层**——把会话上下文按 T0/T1/T2 分层加载，避免上下文塞满丢状态。下面三页分别拆开看。"

---

#### Slide 7 — 三角色协作图

**布局：** 三角色框 + 单向交接箭头

```
┌──────────────┐  规格+features.json   ┌──────────────┐  代码+commits  ┌──────────────┐
│   Planner    │ ───────────────────► │  Generator   │ ─────────────► │  Evaluator   │
│ (Claude CLI) │                      │ (Claude CLI) │                │   (Codex)    │
│ 拆需求 / 写  │ ◄─────────────────── │ 实现/修复    │ ◄───────────── │ 设计测试 +   │
│ ADR / 仲裁   │ done 阶段反馈        │              │ PASS/FAIL+回归 │ 验收 +写报告 │
└──────────────┘                      └──────────────┘                └──────────────┘

铁律：测试设计权 100% 归 Evaluator · Generator 不准写自己的测试 · Planner 不准改产品代码
```

> **讲稿（80 秒）：**
> "三个角色我用了不同的工具来分担。Planner 和 Generator 是 Claude CLI 在不同阶段切换；Evaluator 用 Codex——故意用不同工具，强化"无人评估自己工作"。**Planner 做规划层**：把需求拆成 features.json、写规格文档、做架构决策、出现争议时仲裁。**Generator 做实现层**：按 features.json 一条条实现功能，每完成一条就 push、commit message 必须能对应 features.json 编号、**他不能写自己的测试**——这是铁律。**Evaluator 做验收层**：完整拥有"测试域"，自己设计测试用例、自己执行、产出 PASS/PARTIAL/FAIL 报告；critical 修复必须同 commit 补回归测试。这套分工的关键是——任何一方都没办法越界改另一方的领域。我亲自踩过坑：早期让 Planner 角色"顺手改一行 bug" → 后来发现这一行 bug 修改没经过 Generator 的实装流程也没经过 Evaluator 验收 → 上线后才发现引入新问题 → 这条踩坑沉淀成"铁律 9：紧急 hotfix 也必须走流程"。"

#### Slide 8 — 状态机：7 状态硬约束

**布局：** 状态流转图

```
   new ──► planning ──► building ──► verifying ──► fixing ⟷ reverifying ──► done
                ↑           ↑              │           ↑              │
                │           └──────────────┘           └──────────────┘
                └─── 全 codex 任务 ───────► verifying（跳过 building）

每个状态只允许特定角色操作；progress.json 的 status 字段是唯一真理源
```

> **讲稿（55 秒）：**
> "7 个状态硬性流转。new → planning → building → verifying → fixing ⟷ reverifying → done。每个状态只允许一种角色干活。AI agent 启动时第一件事就是读 progress.json 的 status，如果不匹配自己角色就直接退出。这就是为什么 AI 不可能"越权"——不是靠它自觉，是状态机硬不让它干。还有一个细节：每条 feature 有 executor 字段标"generator"或"codex"，Codex-only 批次（比如压测、安全审计）会跳过 building 直接进 verifying。"

---

#### Slide 9 — 记忆分层 + 跨设备协作

**布局：** 三层加载金字塔 + Git 同步示意

```
T0 (每次启动必读 ≤30 行)：MEMORY.md + project-status.md + environment.md
        ↓
T1 (按当前角色加载 ≤50 行)：role-context/{角色}.md
        ↓
T2 (触发条件命中加载)：feedback-*.md / reference-*.md / user-role.md

  ┌─ 本机 A ─┐  git push     ┌─── GitHub ───┐  git pull     ┌─ 本机 B ─┐
  │ Claude   │ ────────────► │ .auto-memory │ ────────────► │ Codex    │
  │ Planner  │               │ progress.json│               │ Reviewer │
  └──────────┘               └──────────────┘               └──────────┘
```

> **讲稿（75 秒）：**
> "AI agent 最大的隐患是上下文塞满后丢状态。我用三层确定性加载来管它。**T0 永远读**：项目状态快照 + 环境信息，每文件不超过 30 行。**T1 按角色读**：你是 Planner 才读 planner.md，不混读。**T2 按需读**：只有触发条件命中时（比如 UI 起草）才加载对应文件。这种分层让上下文永远精炼。**Git 是协作总线**：所有状态文件、记忆、规格都纳入 git；agent 启动第一步必跑 git pull —— 这意味着我可以早上在台式机用 Claude 当 Planner，下午换笔记本用 Codex 做 Reviewer，状态完全无缝。这套机制后来被沉淀进框架 v0.5.0 版本。"

### Section 4 — 验证：实战数据 + 教训曲线（3 min / 2 slides）

#### Slide 10 — 22 天实战 KPI

**布局：** 三组指标卡 + 一行洞察总结

```
┌─ 交付密度 ──────────┐  ┌─ 验收质量 ─────────┐  ┌─ 时间分布 ───────────┐
│ 22 天 / 982 commits │  │ 103 份验收报告      │  │ 42 个独立批次          │
│ 平均 45 commit/天    │  │ 全部留痕             │  │ 平均批次 ≈ 4-6 小时   │
│ 高峰单日 78 commits  │  │ 14 份 ADR 决策记录   │  │ 上线 buffer 5/13 -3天 │
└─────────────────────┘  └────────────────────┘  └──────────────────────┘

洞察：用 framework 强约束「无人自评」+「测试设计权归 Evaluator」后，
      Generator 在写代码阶段就主动反推「这功能怎么验收」，spec 质量被前置推高
```

> **讲稿（70 秒）：**
> "数据告诉我们什么。**交付密度**：22 天 982 个 commit 平均每天 45 个，高峰单日 78 个；**验收质量**：每个批次都有独立验收报告，103 份全部留痕，14 份 ADR 长期决策；**时间分布**：42 个独立批次，平均每批次只用 4-6 小时从 planning 到 done。这背后的关键洞察是——当框架强制 Evaluator 拥有完整测试设计权时，Generator 在写代码阶段就会主动反推"我这功能怎么验收"，spec 质量被前置推高，反而减少了后期 fix。也就是说，"严格分工"不是低效，是把后期成本前移成了前期质量。"

#### Slide 11 — 框架 30+ 版本 = 30+ 次实战教训

**布局：** 时间轴展示几个关键版本对应的真实事故

```
v0.1.0 (4/04) ─────────────────────────────────────► v0.9.20 (5/10)
     │                                                       │
   初版规则                                          30+ 个版本

代表性版本（每条都是一次真实事故沉淀）:

▼ v0.5.0  共享记忆分层（T0/T1/T2）         ← 上下文塞满丢状态事故
▼ v0.7.1  Spec 起草前必 grep 实物代码      ← 字面假设导致的回归
▼ v0.9.0  Pre-Impl Audit 模式             ← Generator 开工前发现 spec 错
▼ v0.9.4  铁律 #10：commit-tag 必对应 feature ← Planner docs commit 误带
                                              Generator WIP 9 文件入 main
▼ v0.9.11 状态机 JSON 必跑 json.load 校验  ← progress.json 缺一个 } 入 main
▼ v0.9.18 auth role enum 实物核查         ← 字面 'admin' vs 真实 'tenant_admin'
▼ v0.9.19 External API zod schema 实物    ← 单测 mock PASS 但 prod 真数据失败
                                              50/41 row 触发 zod parse error

诚实点：这些都是踩出来的，不是设计出来的
```

> **讲稿（80 秒）：**
> "我想花一分钟讲诚实的部分。框架不是我一开始就设计完美的——它从 v0.1.0 迭代到 v0.9.20，超过 30 个版本，每个版本背后都是一次真实事故。举几个例子。**v0.5.0 共享记忆分层**：起因是早期 AI agent 上下文塞满后，第二次会话完全不知道上次做了什么——这才有了 T0/T1/T2 分层的设计。**v0.9.4 铁律 10**：起因是 Planner 角色的 AI 在 commit docs 时，工作树里还有 Generator 没 commit 完的 9 个 WIP 文件，结果一次性都打包进了 main，需要 revert 重做——所以加了"commit 前必须 git diff --cached 确认 staged 索引"这条铁律。**v0.9.19**：起因是 zod schema 严格化通过了所有单测，但部署到 prod 真数据上 50 个 KOL 里 41 个解析失败——单测 mock 用的是文档假设的 shape，跟真实 API 返回不一致。这条沉淀成"外部 API response 必须 SSH 拉真数据 sample 验证 zod schema"。这些不是设计出来的，是踩出来的。我把它们都沉淀进 framework，下个项目就不用再踩。"

### Section 5 — 复用经验与教训（4 min / 2 slides）

#### Slide 12 — 工程层 7 条经验（给工程师 / Tech Lead）

**布局：** 两列经验卡 + 末尾横通栏

```
┌─ 设计系统先行 ────────────────┐  ┌─ Pre-Impl Audit ──────────────┐
│ 第一个批次必须是设计系统       │  │ Generator 开工前主动审计      │
│ 不是第一个业务页面             │  │ spec vs 实物代码 → Planner 裁决│
│ Why: 后期返工成本是前期 5x     │  │ Why: 字面假设撞实物 = 高成本   │
└───────────────────────────────┘  └───────────────────────────────┘

┌─ CI 红不开新功能 ─────────────┐  ┌─ Critical 修必带回归测试 ─────┐
│ 每次 push 后必查 gh run        │  │ 修复同 commit 补 regression   │
│ 红色立即停手，不堆累积修复     │  │ Why: 不补 = bug 一定回归       │
└───────────────────────────────┘  └───────────────────────────────┘

┌─ 单功能单 migration ──────────┐  ┌─ 视觉规范 ±2px / ΔE<2 ────────┐
│ 不打包 schema 变更             │  │ pixel-perfect 写进验收标准    │
│ Why: 回滚粒度对应风险粒度      │  │ Why: 模糊标准 = AI 输出不收敛 │
└───────────────────────────────┘  └───────────────────────────────┘

┌─ ADR 沉淀关键决策 ────────────────────────────────────────────┐
│ 跨批次影响 / 不可逆 / 当时辩论过 → 写 ADR；本项目 14 份         │
│ Why: AI agent 长期协作需要决策"长期记忆"，否则反复辩论同一问题 │
└─────────────────────────────────────────────────────────────────┘
```

> **讲稿（85 秒）：**
> "工程层的经验我浓缩成 7 条。**设计系统先行**——不要第一个批次就做业务页面，第一个批次必须是设计系统，否则后期返工是 5 倍成本。**Pre-Impl Audit**——Generator 开工前先审计 spec 跟实物代码差异，发现差异就请 Planner 裁决，不要自作主张往下做。**CI 红色不开新功能**——这条看似常识，但 AI agent 没有"自觉"，必须靠规则强制。**critical 修必带回归测试**——验收时检查同 commit 必须有 regression，否则同样 bug 一定回归。**单功能单 migration**——schema 变更不能打包，回滚粒度要对应风险粒度。**视觉规范量化到像素**——pixel-perfect 标准 ±2px / ΔE<2 / 字号 100% / 布局 100%；写得模糊 AI 输出就不收敛。**ADR 沉淀关键决策**——AI 长期协作需要决策"长期记忆"，否则反复辩论同一问题，本项目沉淀了 14 份 ADR。"
